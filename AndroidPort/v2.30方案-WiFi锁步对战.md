## 为什么锁步是"零新机制"

v2.19/v2.20 已经做完了两件难事:

| 已有能力 | 证据 |
|---|---|
| 固定 30Hz 定步长 tick | `Game.tick` / `Game.update(dt)` |
| 指令流:每个命令带 tick 与实体下标,`applyCommand` 重放 | `Game.recordOrder` / `loadReplay` / `injectReplay` |
| 确定性:同一指令流两次跑,`stateHash` 每秒采样全等 | `[v220]` replay determinism 断言 |
| RNG 固定种子 | `Game.rnd = new Random(12345)` |

也就是说"两台机器跑同一张图、同一指令流 → 同一结果"**已经被断言
证明过**。锁步要做的只有一件事:**保证两台机器在同一个 tick 拿到
同一批命令,并且按同一顺序执行**。这正是本期唯一的新代码。

## 批次A:`core/Lockstep.java`

一个回合 = 一个 tick(`TURN_HZ = 30`,与渲染/模拟同频)。

- `submit(player, turn, cmd)`:收下某个玩家在某个回合的命令,并把
  该玩家标记为"本回合已上报";
- `ready()`:**所有**玩家都上报了当前回合才为真——少一个就停,
  这就是锁步的"等待慢机";
- `release()`:把当前回合的命令按 **玩家 id 升序** 排出规范顺序返回,
  然后 `turn++`。规范顺序是两台机器唯一必须一致的东西;
- `desync`:双方定期广播 `stateHash`,不一致就记下回合号并置
  `desyncTurn`(观战/回放里这是"有人作弊或版本不同"的证据)。

命令**复用回放格式**,不发明新语法:

```
wire  : L <turn> <player> <cmd>
cmd   : <verb> <idx,idx,...> <args>          (与 replayLog 完全一致)
```

于是**一场对战序列化出来就是一份合法回放**——这是本方案最想要的
性质:网络层、回放层、断言层共用同一条指令通道,不存在"联机专用
的隐藏状态"。

## 批次B:`Game` 接入(最小改动)

- 新增字段 `public Lockstep lockstep;`
- `recordCommand` / `recordOrder` 改为**先喂锁步**:有 session 时
  命令进 `Lockstep` 而不是进 `replayLog`(无 session 时行为一字不变);
- `update(dt)` 开头:`lockstep != null` 时,未 `ready()` 就**直接
  return**(这一帧不推进);`ready()` 则 `release()` 出来的命令
  逐条 `applyCommand`——和回放走的是同一个函数。

关键性质:本地玩家自己的命令也走同一条路,所以**本地命令同样在
下一回合生效**。这不是延迟 bug,是锁步的定义;真机上由 30Hz 的
一帧(33ms)掩盖,手感上等于"立刻"。

## 批次C:`[v230]` 断言(全部无头可测)

1. **两条链路同源**:同一串命令,一条走 `recordOrder`+`serializeReplay`
   再 `loadReplay`,另一条走 `Lockstep.submit`+`release`,两边
   `stateHash` 采样序列**全等**;
2. **到达顺序无关**:把同一批命令按正序 / 倒序 / 交错三种顺序
   `submit` 给 `Lockstep`,三次 `release` 出来的**规范顺序完全一致**
   (这是锁步的命门,也是最容易写错的一行);
3. **规范顺序 = 玩家 id 升序**:构造两个玩家同回合都有命令,
   断言输出按 player 升序;
4. **等慢机**:缺一个玩家的上报 → `ready()==false` 且 `release()`
   不推进 turn;补上之后立刻 ready;
5. **空回合也要上报**:零命令的回合同样要心跳,否则对面永远等;
6. **不同步可检出**:两边 `stateHash` 不一致 → `desyncTurn` 被置,
   且值等于出问题的回合;
7. **线协议往返**:`encode`→`decode` 逐字段一致,含带逗号下标的
   复杂命令;未知动词/坏行不抛异常(与 `loadReplay` 同样的宽容);
8. **对战即回放**:一整场 session 的 `serialize()` 输出能被
   `loadReplay` 读进去,并重放出与联机时**相同**的 `stateHash` 序列。
