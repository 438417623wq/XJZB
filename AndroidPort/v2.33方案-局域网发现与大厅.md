## 批次A:`core/LanBeacon.java`

主机周期性广播一行文本(和指令流同一套行分帧写法,`\n` 结尾):

```
XJZB-LAN-1 host <房主名> map <地图> players <人数> port <端口>
           version <版本> seed <种子> diff <难度>
```

客机按三条规则过滤,不匹配的**直接忽略而不是报错**——广播网段里
可能有别人的房、旧版本的房、甚至无关的 UDP 流量:

1. `version` 不同 → 忽略(两个版本不能对局);
2. 前缀不是 `XJZB-LAN-1` → 忽略(不是我们的协议);
3. 其余字段解析失败 → 忽略(整行当垃圾丢掉,不抛)。

## 批次B:`core/Lobby.java`

一个大厅就是 N 个槽位 + 三个状态:

```
slots[i] = {name, connected, ready}
canStart() = 所有槽都 connected 且 ready 且人数 >= 2
```

- `join(name)` → 分配最小空槽,满则返回 -1;
- `setReady(i, b)` / `leave(i)`;
- `canStart()`:少一个人、或有一个人没点"准备",都不许开;
- `start()`:**只能成功一次**(开完局大厅就作废),返回是否成功;
- `onPeerLost(i)`:开局前掉线 → 清空该槽(别人可以补位);
  **开局后掉线** → 由 `Lockstep` 的"等慢机"负责卡住,大厅不管。

### 为什么"开局前掉线要清槽"是必须的

不然会出现:4 个槽里有 1 个掉线,`canStart()` 永远 false,
房主永远开不了局,而界面上显示"4/4 已连接"。清槽让第 5 个人能补位。

## 批次C:`[v233]` 断言

1. **信标往返**:`encode`→`decode` 逐字段一致;
2. **过滤规则**:版本不同、前缀不对、字段残缺、纯垃圾 —— 四种都
   必须**返回 null 而不是抛异常**;
3. **入座**:`join` 依次填 0,1,2…;满员后返回 -1;
4. **掉线清槽**:中间槽掉线后,下一个 `join` 补上那个空位;
5. **开局门禁**:全员已连接但有人没准备 → `canStart()` false;
   全员准备 → true;人数不足 2 → false;
6. **只能开一次**:`start()` 第二次返回 false;
7. **开局后掉线不再清槽**(由锁步负责),`start()` 后
   `onPeerLost` 不影响已开始的对局;
8. **与握手串起来**:大厅产出的 `(map, players, seed, version)`
   直接喂 `Handshake`,两台机器算出的握手应当互不拒绝。
