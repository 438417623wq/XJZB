## 八之三十二、v2.32:流式分帧 + 开局握手

v2.31 的 `Link.send(String)` 假设**消息边界被保留**——进程内是真的,
**真实 TCP 上不是**。TCP 是字节流:一次 send 可能拆成两个包,两次
send 可能合成一个包。本期补上这一层并测出来。
`GameDesktop` 新增 `[v232]` 段 1 项(8 个子断言),全量 **101 项 PASS**。

### 新增

- `core/LockstepStream.java`:行分帧(`\n` 结尾 UTF-8)。选它的理由:
  指令行本来就是文本且**不含换行**(见 `commandFor`),不用转义;
  抓包/日志肉眼可读,和回放文件同一套写法;半包/粘包从"协议问题"
  降级成"接收侧缓冲区问题"——**收满一行才交付**;
- `core/Handshake.java`:开局前核对 `version/map/players/seed`
  (**致命**,任一不同就拒),`race/difficulty` 只**提示不拒**。
  拒绝消息**点名是哪一项**——"连不上"对玩家毫无信息量,
  "地图不一致:divide vs hunters" 才能让人去改;
- `LockstepLink.Hub` 新增 `chop` 模式:每行编码成字节后**按随机
  小片**交付,接收端用 `LockstepStream` 重组;并且**每次 poll 只
  放行有限片数**(`chopPerPoll`)——如果一次 poll 就把所有片喂完,
  一行永远在一次 poll 内重组完成,"半包跨帧"这个最有意思的情况
  就永远测不到。真实 socket 的 read 返回的就是"缓冲区里现在有的",
  常常不足一条完整消息。

### `[v232]` 断言(8 条子断言)

1. **切法无关**:同一串消息按 1 字节 / 3 字节 / 7 字节 / 整块 /
   混合切法喂进去,出来的行序列**全等**;含一条**中文**指令,
   所以切片会落在多字节 UTF-8 字符中间;
2. **粘包**:两条消息合成一次 `feed` → 出来两行;
3. **半包**:一行拆成多次 `feed`,补齐之前 `lines()` 为空;
4. **CRLF 容错**;
5. **握手放行**:六项全同 → `reject` 返回 null;
6. **逐项拒绝并点名**:version / map / players / seed 各改一项,
   都必须被拒**且原因里出现对应中文关键词**;
7. **race/difficulty 只提示不拒**;握手行畸形不抛异常;
8. **端到端**:把一条真实命令(`Lockstep.encode` + `LockstepStream`)
   按 **3 字节**切碎喂进去,对面解出来与直接投递**完全一致**。

### `[v231]` 顺势加强

两台机器的对拍从 3 组链路参数扩到 **5 组**,其中最后两组打开
`chop`——两台机器现在是在**字节流**上跑锁步,而不是靠进程内
消息边界"作弊"。断言仍全绿。
