## 八之三十五、v2.35:真实 TCP 环回双机对拍

到这里为止,锁步协议**全部**是在**进程内的假链路**上验证的。
那是验证规则的正确方式,也是**发现规则扛不住 socket**的错误方式。
本期用 `ServerSocket`/`Socket` 在 127.0.0.1 上跑**两个真线程
两个真连接**的对局,把同一个不变量换一个执行环境再测一遍。

### 为什么不能省

`[v231]`/`[v232]`/`[v234]` 的 Hub 是我自己写的:按帧投递、按帧
poll、按帧推进。真实 socket 没有"帧"——`read()` 返回缓冲区里现在
有的字节,可能不足一条消息,也可能是三条粘在一起;两个线程的
调度顺序不确定。这三件事组合起来足以让一个"逻辑上正确"的锁步
实现**死锁**(两边都在等对方先动)。

### 新增 `tools/TcpLockstep.java`

- 主机 `ServerSocket` 接受连接跑玩家 0,客机 `Socket` 连接跑玩家 1;
- 每端一个**读线程**:`read(buf)` → `LockstepStream.feed` → 取完整行
  (锁保护);主循环每帧只取走**已到达**的行,不阻塞;
- 关键点:**读线程与主循环分离**。若主循环自己阻塞读,两个玩家会
  互相等(都在等对方字节才肯上报),直接死锁;
- 实测(连跑 4 次):

```
tcp match commonTurns=227 diffTurns=0 aTurns=228 bTurns=227 samePerTurn=true PASS=true
tcp match commonTurns=226 diffTurns=0 aTurns=227 bTurns=226 samePerTurn=true PASS=true
tcp match commonTurns=222 diffTurns=0 aTurns=222 bTurns=223 samePerTurn=true PASS=true
tcp match commonTurns=227 diffTurns=0 aTurns=227 bTurns=227 samePerTurn=true PASS=true
```

`diffTurns=0` 每次都成立;两边回合数差 ≤1 是线程调度抖动的正常
表现(一边先跑完循环),不是发散。
