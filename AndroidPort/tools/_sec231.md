## 八之三十一、v2.31:双机锁步联调(无头)——延迟/抖动/乱序下的两台机器

v2.30 证明了**一台**机器跑一条指令流 = 一份回放。但那句话对
"**两台**机器在同一批命令下保持同一状态"什么都证明不了。本期把它
**实测出来**:两个各自独立模拟的 `Game`,通过一条**有延迟、有抖动、
会乱序**的链路交换命令,逐回合 `stateHash` 全等。
`GameDesktop` 新增 `[v231]` 段 1 项(7 个子断言),全量 **100 项 PASS**。

### 新增

- `core/LockstepLink.java`:`Link`(send / poll)+ `Hub`(进程内星型中继)。
  Hub **故意不友好**:每条消息延迟 `latency + rnd(jitter)` 帧、允许
  同帧到期消息乱序投递;**不模拟丢包**——发现走 UDP 广播,指令流走
  TCP,所以"包丢了"不是这套协议的语义,延迟/抖动/乱序才是 TCP 也会
  交给应用的东西,也正是锁步必须扛住的东西。内部 `Random` 固定种子,
  同一组参数每次跑都完全一样;
- `core/LockstepPeer.java`:一台机器 = 一个 `Game` + 一个 `Lockstep` +
  一条链路。对外只有三相位:`receiveFrame()` / `sendFrame()` /
  `stepFrame(dt)`;
- `[v231]` 断言:三组链路参数(0/0/0、1/3/0、2/5/1+乱序)各跑 20 秒,
  两台机器的**每一回合** `stateHash` 全等、回合数不发散、指令日志
  逐条相同、序列化出来的回放体完全相同。

### 三个真 bug(都是"只有两台机器才暴露"的那一类)

1. **心跳在线上解不开**。`encode(0, 1, "")` 生成 `"L 0 1 "`,而
   `decode` 用 `split(" ", 3)` 要求三个字段,于是**心跳解出来是
   null 被丢掉**——一个"没什么可说"的玩家和一个"不在场"的玩家变得
   完全一样,对面于是永远等下去。修法:`encode` 对空命令不发尾空格,
   `decode` 只要两个字段、命令可省略;
2. **心跳会把真命令顶掉**。乱序链路上,同一回合的心跳可能**先于**
   真命令到达;`submitAt` 原来是"先到先得",于是把空占位存下、
   把真正的命令丢了——**只在一台机器上丢**,这就是一次静默 desync。
   修法:按内容而不是到达顺序定规则——真命令永远占位,空心跳只填
   空槽;
3. **一回合发了多次上报**。两台机器的驱动循环每帧都调一次
   `sendFrame()`,于是同一回合往线上发了 N 条上报;有延迟时它们
   先后到达,对面按先到的算,于是两台机器对"这个回合是什么"看法
   不同。修法:`LockstepPeer` 记住本回合是否已上报,
   `sendFrame()` 每回合**只发一次**,后调用是 no-op。

### 断言写错一次(记录下来)

第一版断言按**帧**比对两台机器的 `stateHash`,于是必然失败——
一台在等对面上报时是**冻结在旧回合**的,任何一帧两边的进度都
可以合法地不同。锁步保证的是"**同一回合结束后状态相同**",不是
"同一帧状态相同"。改成**按回合**取哈希再比对,断言才成立。
这一条写进断言注释了,免得下一个人再踩。
