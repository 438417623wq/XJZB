## 八之三十八、v2.38:断线判负真正接进对局(修"测了没人调用")

v2.34 断言了超时规则,v2.37 断言了 socket 层,但**两边都没让应用
真的去做那件事**:`forfeit()` 没有任何调用点。于是真机上对面
**杀掉进程**之后,幸存方会**永远卡在同一个回合**上——正是 v2.34
想解决的那个"死机"。**被测了却没人调用的逻辑不是功能。**
`GameDesktop` 新增 `[v238]` 段 1 项(5 个子断言),全量 **106 项 PASS**。

### 两个信号,缺一不可

- **慢信号(已有)**:对方还连着但不再应答(进程被杀/息屏/掉 wifi),
  `stallTurns` 连续累积到 `STALL_LIMIT`(300 帧 = 10 秒)判负;
- **快信号(本期)**:`Link.isClosed()` —— 传输层**已经知道**对方没了
  (FIN 到了)时立刻判负,不必再等 10 秒去等一个**答案已知**的计时器。
  实测:客机 `close()` 之后,主机在**第 1 帧**(约 20ms)就判出
  `forfeitLoser=1`,而不是 10 秒。

### 实现

- `LockstepLink.Link` 加 `default boolean isClosed() { return false; }`
  —— 默认实现让**进程内 Hub 一行都不用改**(它没有 socket,不会失败),
  桌面断言因此完全不受影响;
- `LockstepPeer.checkForfeit(limit)`:一个调用点决定"对方是不是走了"并
  记录结果。`stalledOut(limit) || link.isClosed()` → `forfeit(who)`;
- `GameView` 的对局循环在 `stepFrame` 之后调它,判负即写
  `game.status = win/lose` 并提示(写的是 **Game 上的字段**,
  和结算面板/任务记账读的是同一个——第一版写成了视图局部变量,编译不过)。

### `[v238]` 断言(5 条子断言)

1. **闭合的链路立刻判负**(`stallTurns==0` 时就判),且输赢方正确;
2. **开着但沉默的链路**仍在**恰好** `STALL_LIMIT` 那一帧判负,
   提前一帧不行;
3. **一直在应答的对手永远不会被判负**(跑 3 倍限额的帧数),
   而且对局一直在推进(900 回合);
4. 判负之后幸存方**还能继续推进**(回合数继续涨),不会僵住;
5. **端到端真 socket**:客机 `close()` 后,主机在一次 `checkForfeit`
   内就点名它(`afterFrames=1`)。

### 真机复测清单(装 v2.38 后按顺序过)

1. **回归**:遭遇战 / 战役 / 回放三条老路径应与 v2.37 一致
   (本期只改了对局循环里"有 session 时"的那条分支);
2. 双机联机后,**对局中直接杀掉一方进程**:另一方应在**一两秒内**
   弹出"对方已掉线,你获胜"并正常进入结算——旧版本会永远卡住;
3. 对局中一方**切后台 3 秒再回来**:应继续对局,**不算掉线**;
4. 对局中一方**切后台 25 秒再回来**:应已被判负(超过 10 秒);
5. 联机对局里按暂停 →「重新开始」:应提示"联机对战不能重新开始"
   而不是把对局搞成两台机器各走各的。
