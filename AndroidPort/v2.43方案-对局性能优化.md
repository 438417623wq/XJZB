## 一、症状与定性

用户真机回报:「对局有很强的顿挫感,非常卡顿」。

静态取证把「顿挫」拆成两类,它们的成因不同,修法也不同:

| 类型 | 表现 | 成因 | 证据 |
|---|---|---|---|
| **A. 稳态低帧率** | 全程均匀地「沉」,单位越多越明显 | `Game.update(dt)` 每帧多次 O(N²) 全表扫 | 7 处每帧 O(N·N) 循环(见 §1.1);update 与 render 同线程,update 变慢直接吃帧预算 |
| **B. 周期性尖峰卡顿** | 每隔一阵突然一顿(约每 45–85s) | AI 波次发布瞬间全军 `setPath` ⇒ 一帧内几十到上百次 A* | `aiUpdate` 波次分支一次性给全军队 setPath;每次 A* 最多 60000 次扩展 |
| **C. GC 抖动** | 随机的小顿,伴随死亡高峰更明显 | 每帧海量短命对象 | COW 迭代器/数组复制、每实体 2 个 `new Rect`、A* 回溯每节点 `new int[2]`、`Object[]`/`float[]` 事件 |

三类各自对应的处置: A → 空间网格 + 短路(P0);B → 寻路预算化(P0-c);C → 分配削减(P1)。

### 1.1 帧预算算术(为什么 A 是主因)

主循环 `GameView.run()` 是单线程:

```
update(dt) → events → edgeScroll → lockCanvas/render/unlock → sleep
```

- 旧版 `Thread.sleep(14)` 把帧上限压在 ~60FPS;每帧实际预算 ≈ 16ms,其中留给 update+render 的 ≈ 2–15ms。
- update 侧每帧 O(N²) 的 7 处循环(行号为**改动前**的旧值):
  1. separation:`updateUnit`(`:5022-5034`)每单位扫全 ents;
  2. 建筑碰撞:`:5046-5057` 再扫全 ents;
  3. `isCloakedNow`(`:4304-4313`)内嵌 arbiter 环扫,**无条件执行** —— 场上没有一个 arbiter 也照扫;
  4. `detectorNear`(`:4316-4324`)全表扫;
  5. 空闲单位 auto-acquire `findEnemyInRangeFrom`(`:5547-5580`,调用点 `:4924-4932`);
  6. `updateEconomy`(`:4603-4641`)supply 两遍全表 + 空闲工人 `nearestMineral`(`:4650-4662`);
  7. `updateFog`(`:4591-4601`)全图衰减 + 每玩家单位 revealAround。
- N=200 时 ≈ 7×200×200 = **28 万次**迭代/帧;N=400 时 ≈ **112 万次**。按手机上每次迭代 10–30ns 计,仅这 7 处就是 3–30ms。
- 渲染侧同样全量遍历 ents 且 `drawEnt` **无视口剔除**,屏外单位照样 `bank.get` + 阴影 `drawOval` + `drawBitmap`。

### 1.2 B 类尖峰算术

- 工人每趟矿 `setPath` ×2、attack-move 每次找敌重新 setPath —— 常态小尖峰。
- AI 波次一次给 50–100 个单位 setPath ⇒ 50–100 次 A*,每个最多几万次扩展 ⇒ 单帧可超 100ms,就是玩家看到的「每隔一阵猛顿一下」。

### 1.3 C 类 GC 清单

- `ents` 旧为 `CopyOnWriteArrayList`,Game 内 61 处 for-each 每次迭代都 new 迭代器;16 处 add/remove 都复制整个底层数组(N=400 时每次 ≈1.6KB),死亡高峰一帧几十个 remove。
- 渲染:每实体 2 个 `new Rect`,`SpriteBank.frameRect` 再 new 一个;尸体/动画各 2 个。
- 逻辑:A* 回溯每节点 `new int[]{c % wMini, c / wMini}` + `Collections.reverse`;事件 `List<Object[]>`;特效 `List<float[]>`。
- `Thread.sleep(14)` 是定值:工作耗时 5ms 时帧长 19ms(≈52FPS)且抖动,不做帧目标对齐。

## 三、P0 落地实况(update 侧 O(N²) 消除)

### 3.1 统一空间网格(`core/Game.java`)

- `:1356-1386` 大段注释:**ORDER IS THE CONTRACT**。七个循环原本每 tick 每单位走全表(200 单位 = 28 万次门评估),而三处语义**依赖遍历顺序**:separation 累加 float 和、建筑碰撞边算边改位置、nearest 助手「第一个严格更近者胜」。因此 `gatherNear()` 必须按 **roster 序号升序**交还候选。
- **cell = 64 世界 px**(方案原提案 128,**实际落地 64**):`:1389` `private static final int GRID_CELL = 64;`。
- `:1403` `private static final int GRID_MARGIN = 64;`(注释:一整个 cell 的余量是现实最坏值的 16 倍,覆盖建筑推出把单位瞬移数十 px 的情形)。
- `:1405-1421` 字段:`spatialValid`、`gridW, gridH`、`int[] cellCount`、`int[] cellStart`(`gridW*gridH+1` 前缀偏移)、`int[] cellItems`(roster 序号,cell 主序,cell 内按 roster 序)、`int[] qScratch = new int[256]` + `qScratchN`、`Ent[] bldList = new Ent[64]` + `bldListN`、`Ent[] dropList = new Ent[32]` + `dropListN`、`statGridRebuilds/statGridQueries/statGridCandidates`。

## 四、P1 落地实况(GC/分配削减)

1. **`ents` 从 CopyOnWriteArrayList → ArrayList**:`:1196-1210` `public final List<Ent> ents = new ArrayList<>();`(注释:同线程读写,唯一跨线程通道是 `pendingOrders`)。
   - 连带必须改的两处**索引循环**(否则语义或异常都错):

## 五、P2 落地实况(渲染侧)

1. **视口剔除**:`GameView.java:233-278` 注释块 + 三个 gate。
   - 关键决策:取对象**实际 extents** 而非固定 margin。理由(注释原文要点):本作 extents 跨两个数量级 —— marine cell 128px,而爆炸 cell(`plasma`/`bang_l`/`nukehit`)达 256px 且动画 scale 最高 1.4,固定半径要么太小(爆炸在屏幕边缘消失)要么大到剔不掉任何东西。
