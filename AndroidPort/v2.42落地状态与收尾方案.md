### 6.1 已修 bug:`set:diag` 路由缺失

`handleButton` 的白名单只管 `menu:` / `set:back` / `set:edge` / `set:hp` /
`set:fog*` / `set:zoom*` / `set:layout*`;`set:sens`/`set:hold`/`set:vol` 有专门分支。
设置页 10 个控件里**只有 `set:diag` 两条路都没走** → `handleMenu` 的
`case "set:diag"` 不可达,`renderDiag` 恒为 `false`。

修复:`GameView.java:4690` 白名单加 `|| "set:diag".equals(b.action)`
(注册点 `:2645`,`case` 在 `:5195`)。

### 6.2 插桩强化:让一张截图 / 一段 logcat 就能定层

原插桩不足以定案:清屏色 `Color.rgb(6, 8, 12)` 本身近黑,截图无法区分
「裸画布/dst 缝隙」与「合法的深色地形」;0.5Hz 日志会漏掉只持续几帧的甩动。

| 插桩 | 位置 | 作用 |
|---|---|---|
| 清屏色条件式 | `GameView.java:1124` `settings.renderDiag ? Color.rgb(0,255,0) : Color.rgb(6,8,12)` | 屏幕上仍是黑的像素 = 被真实几何覆盖;变绿 = 裸画布,即 dst 覆盖缝隙 |
| chunk 1px 描边 | `:1240` 段,颜色按 `(cx+cy)&1` 取青/橙 | 黑条在框内(bitmap 内)还是框间(dst 缝隙)一眼可辨 |
| 未解码块整块洋红 | `:1253` `Color.argb(110,255,0,255)` | 洋红块 = 未解码 chunk;有黑条而无洋红 → 排除解码路径 |
| 逐帧 miss 日志 | `:1263` 段,上限 400 条 | `[diag-miss] f= chunk=<cx>_<cy> cam= zoom=`;同一行也进屏上面板 |

### 6.5 根因定案:相机字段跨线程共享,一帧被两台相机画

真机截图(a1/a2,2608×1200,divide,zoom=1.56,开着渲染诊断)给出了三个无法用
「解码缺失」「资产」「覆盖层」解释的事实:

1. **黑条处是纯绿**。绿 = 清屏色 `Color.rgb(0,255,0)`,即**没有任何绘制盖住那一带**。
2. **a2 面板显示 `miss 本帧=0  峰值=0`**,却在同一帧有大片绿带
   ⇒ 不是「chunk 没解码出来」,每个可见块都 `drawBitmap` 了。
3. **绿带是阶梯状,边界精确落在 chunk 网格线上**:a2 四级阶梯的右边界
   788/1578/2366 与纵向描边线完全重合,每级宽 ≈790px = 512×1.54。
   ⇒ 缺的是**整列 chunk 的 dst**。

决定性证据来自 `tools/_camfit2.py`(逐区域二维最小二乘拟合相机,zoom=1.56,
双线性采样 16 个 divide chunk 拼成的 2048×2048 世界图):

```
== a2.jpg
   above-L  (100, 700, 400, 610)   -> cam=(834.5, 500.0)  mean|diff| 6.74
   above-M  (900, 1500, 440, 650)  -> cam=(840.5, 474.5)  mean|diff| 4.02
   above-R  (1700, 2300, 480, 685) -> cam=(846.0, 450.5)  mean|diff| 4.12
   below-L  (100, 700, 765, 975)   -> cam=(853.5, 413.5)  mean|diff| 10.52
   below-M  (900, 1500, 765, 975)  -> cam=(853.5, 413.5)  mean|diff| 4.19
   below-R  (1700, 2300, 765, 975) -> cam=(853.0, 409.0)  mean|diff| 4.12
```

**同一帧的上半条带拟合出 camY≈450–500,下半条带拟合出 camY≈409–413.5,
camX 也从 834.5 漂到 853.5** —— 一张截图里叠着两套相机。进一步用纵向描边线
反解(`sx(512)+4 = 边界`)得到两套网格:a2 的网格 A 间距 790 ⇒ zoom=1.543,
网格 B 间距 799 ⇒ zoom=1.561(与面板 `zoom=1.56` 吻合)。**两套 zoom 差 1.15%**。

根因:`GameView` 的 `camX/camY/zoom` 是**普通字段**,触摸线程
(`onTouchEvent` 拖动/双指、`edgeScroll`)直接写,渲染线程 `render()` 在一帧内
通过 `sx()/sy()/wx()/wy()` 读它**数百次**(每个 chunk 的 dst、每个实体、每个 HUD
部件)。一旦拖动落在帧中途,前半帧用旧相机、后半帧用新相机,
**相邻 chunk 的 dst 不再相接**,接缝处露出清屏色 —— 关诊断是 `rgb(6,8,12)`
(玩家读作黑条),开诊断是纯绿。这也解释了「只在快速甩动时出现、停下就没了」。

**已排除(静态排查,承接 §6.4)**:资产含绿/透明(全树 0)、解码 miss
(a2 峰值=0 仍有绿带)、`clipRect`/变换(全文件无)、全屏覆盖层(5 处全在模态层)、
雾(只可能是黑)、minimap 缺失(52 图全在)、纯 dst 几何缝隙
(`tools/_geomsim.py` 在 zoom=1.56 下 201×201 相机网格 **0 缝隙**)。

> **教训**:横向「cyan/orange 描边线」检测会被绿带边缘的 JPEG 振铃污染,
> 只有**纵向长线**可用;FFT 互相关(`_camfit.py`/`_patchfit.py`)在本场景
> ncc 只有 0.1–0.4 不可靠,**逐区域最小二乘**(`_camfit2.py`)才给出可用信号。

### 6.6 修复:每帧冻结相机快照

让 `camX/camY/zoom` 成为**渲染线程独占**的相机;触摸线程只把意图发布到
`inCamX/inCamY/inZoom` + `camDirty`,`render()` 在帧首采纳一次。

**为什么不是给渲染加锁**:`sx()/sy()` 每帧被调用数百次,加锁会把锁开销乘上数百,
而且触摸侧仍会阻塞渲染。发布/采纳把同步点压到**每帧一次**。

**为什么触摸侧命中测试仍读 `camX` 而非 `in*`**:玩家点的是**上一帧看到的位置**,
命中测试必须与屏幕一致;若读 `in*`,快速拖动时点击会落到还没画出来的位置上。

`GameView.java` 改动:

| 位置 | 内容 |
|---|---|
| `:50-78` | `private volatile float camX, camY, zoom = 1.3f;` + `private volatile float inCamX, inCamY, inZoom = 1.3f;` + `private volatile boolean camDirty;`(volatile 保证跨线程可见性) |
| `:81-83` | `tCamX()` / `tCamY()` / `tZoom()`:`camDirty ? inCamX : camX` —— 触摸侧算 delta 时读「已经排队的意图」,连续拖动不会丢步 |
| `:94-119` | `tPanTo(x,y)`(**带 clamp**)/ `tPanBy(dx,dy)` / `tCenterOn(x,y)` / `tZoomTo(z)` |
| `:127-130` | `setZoomNow(z)`(UI 侧改缩放档,保留 pending pan) |
| `:138-143` | `setCameraNow(x,y,z)`(重开/构造,两份都写并清 `camDirty`) |
| `:1111-1116` | **`render()` 帧首采纳**:`if (camDirty) { camX = inCamX; camY = inCamY; zoom = inZoom; camDirty = false; }` |
| `:545-546` | 构造时 `inCamX = camX; inCamY = camY;` |
| `:2515` | `applySettings()`:`zoom = Settings.zoomDefault(...)` → `setZoomNow(...)` |

### 7.2 根因

### 7.3 修复

```java

        HudLayout.INFO_H_DP * uiScale * hud.infoScale);
float k = uiScale * hud.infoScale;
boolean multi = sel.size() > 1 && !sel.get(0).isBuilding();
float cap = INFO_CAP_DP * k;
if (multi) {
    float cellS = Math.max(18 * k, Math.min(30 * k, panelH - 48 * k));
    int kinds = kindsOf(sel);
    cap = Math.max(cap, 20 * k + kinds * cellS
            + Math.max(0, kinds - 1) * 5 * k);
}

wantW = Math.max(wantW, 90 * k);
```

```java
private static int kindsOf(List<Game.Ent> sel) {
    java.util.HashSet<String> seen = new java.util.HashSet<>();
    for (Game.Ent e : sel) {
        seen.add(e.type.key);
        if (seen.size() >= 6) return 6;
    }
    return seen.size();
}
```

## 八、事故记录:PowerShell 批改中文源码导致不可逆损坏

### 8.1 事故

把新增注释里的 `v2.43:` 统一改成 `v2.42:` 时,用了:

```powershell
$n = (Get-Content $f -Raw) -replace 'v2\.43:', 'v2.42:'
Set-Content $f $n -NoNewline -Encoding UTF8
```

结果 `GameView.java` 与 `HudPreview.java` 的**中文全部损坏**。

### 8.2 机理

- `Get-Content -Raw` 在 PowerShell 5.x 下按 **cp936(GBK)** 解码 UTF-8 字节 →
  每个中文字符变成 2–3 个乱码字;
- `Set-Content -Encoding UTF8` 再把这些乱码写成 UTF-8,并**加上 BOM**
  (javac 随即报 `错误: 非法字符: '\ufeff'`);
- cp936 无法映射的字节被写成 `?`(0x3F),**原字节永久丢失**,逆变换不可行。
- 指纹:`\xe2\x80\x94`(U+2014 `—`)→ `\xe9\x88\xa5?`(「鈥」+ `?`)。

### 8.3 恢复过程

| 文件 | 恢复方式 |
|---|---|
| `GameView.java` | 有事故前备份 `%TEMP%\GameView.bak`(298107 B,无 BOM,中文完好)→ `Copy-Item` 还原,再用 **Python**(`encoding='utf-8'`)做标签替换 |
| `HudPreview.java` | **无备份**。用 .NET 的 `Encoding.GetEncoding(936)` 把整份损坏文件逆向还原成原始字节(`GetBytes` → `Decode(utf8)`),再用**编译产物** `bin/HudPreview.class` 的常量池(它早于事故)逐字面量校对补齐 —— 55 个自动修复 + 5 个按前缀/后缀匹配 + 8 个按行号手工补 |
| `GameDesktop.java` | **未受影响**(它不含 `v2.43:` 字符串,循环没碰它) |

恢复后核对:三份文件均 `BOM=False`、`U+FFFD=0`、`v2.43=0`;
`javac` exit=0;`[v242]` **111 PASS=true / 0 PASS=false**。

> 注意 Python 的 `cp936` 编解码器**不能**用于此逆变换(它对 GBK 的 PUA 区映射不同,
> 会抛 `UnicodeEncodeError: 'gbk' codec can't encode character '\ue160'`),
> 必须用 .NET 的 `Encoding.GetEncoding(936)`。

### 8.4 铁律

**改含中文的源码,一律用 `edit`/`write` 工具或 Python(`encoding='utf-8'`)。**
禁止用 PowerShell 的 `Get-Content -Raw` + `Set-Content` 做批量文本替换;
批处理前先 `Copy-Item` 一份到 `%TEMP%`。
