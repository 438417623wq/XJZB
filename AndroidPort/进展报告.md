## 二、v2 攻克的三道硬关

### 关 1:WPE 调色板(压缩掩码 0x41)

地形和单位的全部颜色来自 `tileset\<name>.wpe`。这些文件用
**Huffman + ADPCM 复合压缩(掩码 0x41)**,v1 的工具链完全无法读取。

- 按 StormLib 源码(huff.cpp / adpcm.cpp)逐字移植:
  - FGK 自适应 Huffman(数据分布初始权重表 + NYT 转义 + 加权重平衡);
  - ADI 单声道 ADPCM;
- 用「自实现压缩器 ↔ 解码器往返」做自测(4 种数据类型 × 4 种数据全对);
- 再按 v1 解压表顺序(Huffman → ADI)串起来,7 个 WPE 全部解开
  (每项 1024 字节,alpha 字节全 0,颜色渐变合理)。

期间还发现并修复:`StarDat.mpq` 里 **1024 字节的小文件也带扇区偏移表**
(原版格式规定 ≤ 扇区大小的文件不带)。sc_archive 现在会先探测扇区表,
失败再回退单扇区布局——这一个发现同时修复了一大批素材的读取。

### 关 2:GRP 精灵格式(v1 的死因)

v1 用了记忆中的"经典格式"(u32 帧偏移 + 0x80 行终止 RLE),完全解错。
v2 通过 hexdump + 逐符号追踪解压流,发现真实格式:

```
帧头 8 字节:{u8 x偏移, u8 y偏移, u8 宽, u8 高, u32 数据偏移}   ← 8 字节,不是 4!
数据区:u16 行偏移表(每行一个,相对帧数据起点)
行 RLE:0x80|n = 透明跳过 n;0x40|n = n 像素重复下一字节;其余 n = 复制 n 字面量
行解码到 x≥宽 即停(行允许过量编码)
```

关键校验:帧 0 的偏移 = 6 + 帧数×8(表末即数据头);行消耗字节数与
行偏移差值逐行吻合。最终 45 张单位/建筑 GRP 全部解出,
机枪兵 229 帧 = 13 个 17 向动画块 + 8 帧死亡动画。

**单位配色**:调色板 8–15 号位是队伍色梯度,替换成自造蓝/红渐变即得
我方/敌方皮肤(目测验证:蓝色装甲机枪兵/红色小狗)。

### 关 3:盗版重打包的数据缺损

本机 StarDat/BrooDat 为重打包:**每个文件随机若干扇区的解压流尾部缺 1~7 字节**
(流无 END CODE 即终止,文件头 fs 仍记录原始大小)。后果是文件中段整体错位,
v1 的"精灵像素错位"正是这个原因。

方案:**缺口感知读取(GapReader)**——
- 解压时按扇区记录每个洞的(原始坐标, 长度);
- 之后所有结构化读取(帧表、MTXM、单位表)都按**原始坐标**经 GapReader 进行;
- 洞内字节不可恢复,但只损失几个像素/一条记录,不再污染整个文件。

## 三、地形管线(血浴验证案例)

正确链路(经四模型对照 + 连通性验证确定):

```
MTXM u16 ──→ CV5 条目(52B) ──→ u16[0] = VX4 megatile ──→ 16× (flip|VR4 索引)
                                                            │
VR4 minitile(64B,8bpp,8×8 像素)←──────────────────────────┘
颜色 = WPE[像素值];可走性 = VF4[vr4索引] bit0
```

- VR4 是 **8bpp**(每 minitile 64 字节)而非 4bpp——由调色板数值范围实证;
- vf4 bit0=可走:血浴 4 个出生点在 bit0 图上互相连通,四角坐标与真实地图一致;
- 整图渲染(猎手):蓝灰色地面、黑色空间坑、斜坡结构完整——猎手的标志性外观。

产出 9 张地图(64×64 ~ 128×128),每张 = 512px 地形块 PNG + minimap + walk.bin + meta.txt。

## 七之二、v2.2 修复轮(本轮)

这一轮是**回归修复**:v2.1 引入的命令卡/特效/语音其实都没真正生效,
本轮逐条定位并修掉,并用数据驱动的方式(而不是猜索引)重建素材表。

### 1. 攻城坦克「架塔」必崩(功能性 Bug,最高优先级)

`tank` 的 `siegesTo = "stank"`,但 **`stank` 从未注册进 `Game.TYPES`**。
于是 `toggleSiege()` 里 `TYPES.get("stank")` 返回 `null`,紧接着读 `t.hp`
直接 NPE —— 也就是说 v2.1 的招牌功能一按就闪退。

- 用桌面验证台写了一个最小复现(`tools/_siegetest/SiegeTest2.java`),
  确认 `*** CRASH: NullPointerException ... at Game.toggleSiege(Game.java:621)`。
- 补上 `stank` 类型(不可移动、射程 280、伤害 45),并让 `siegesTo` 双向可逆。
- 复测:`toggleSiege -> true newKey=stank`,后续 10 tick 无异常。

### 2. 架塔按钮点不到(交互 Bug)

`GameView` 把「架塔」按钮画在了**和「停止」完全相同的矩形**上:

```java
addBtn(bx - (bs + gap), by + 8 * uiScale, bs, "stop",  "停止");
addBtn(bx - (bs + gap), by + 8 * uiScale, bs, "siege", "架塔");  // 同一格
```

而 `handleButton()` 命中第一个就 `return` —— 所以架塔永远轮不到。
现在架塔独占第三格,并区分 `siege` / `unsiege` 两个动作与图标。

### 3. 命令图标索引全错(素材 Bug)

v2.1 的 `ICONS_WANT` 是手猜的编号,导致 SCV/喷火兵/坦克/导弹塔/地堡
按钮显示的是别的单位(导弹塔显示成了补给站,坦克显示成了 22×20 的碎片)。

本轮改为**从游戏自身数据推导**:`cmdicons.grp` 的帧号 == `arr/units.dat`
的单位 ID(已用三个 MPQ 交叉校验 30 个关键帧的哈希,SD/PT/BD 一致)。
于是机枪兵=0、坦克=5、SCV=7、喷火兵=10、指挥中心=106 …… 命令键从 228 起。
重渲染逐帧核对,图标与单位精灵一一对应。

### 4. 爆炸/死亡特效从未产出(素材 Bug)

`pipeline_sprites.py` 里写的路径是 `thingy\tBangS.grp`,**漏了 `unit\` 前缀**,
三个爆炸 GRP 全部 `MISS`,从未写进 assets。

- 用 `arr/images.tbl`(719 条 GRP 路径表)反查出真实路径
  `unit\thingy\tBangS.grp` / `tBangL` / `tBangX`。
- 顺带提取单位死亡序列:机枪兵/小狗/刺蛇的 GRP 尾帧
  (`marine` 229 帧 = 13 个 17 向块 + 8 帧死亡),以及通用 `tmeDeath`。
- 核心新增 `Game.Anim` + `Game.playAnim()`,按固定帧时长播放一次性动画;
  渲染层在实体之后、粒子之前绘制,队伍色随 `_b`/`_r` 切换。

### 5. 虫族与坦克语音根本没提取(素材 Bug)

`sfxdata.tbl` 只读了 StarDat,而**虫族单位语音在 BrooDat 的表里**;
坦克语音的真实名字也不是 `SIEGETANK\TSg*`,而是 `Terran\TANK\TTa*`。
结果:所有虫族/坦克语音 `MISS`,回落到建筑音。

修复后音效从 19 个涨到 **39 个**(含 scv/marine/firebat/vulture/tank/
zergling/hydra/muta/drone 的 ready/what/ack/die 全套)。

### 6. 标题画面解码错误(素材 Bug)

`pcx_decode()` 两处错误:

## 八、v2.4:调色板纠错 + 五批反馈/表现/UI 落地

### 0. 先修了一个比所有批次都大的底层 Bug:红蓝通道全反

接批次三(枪口火光)时发现提取出来的 `tmeFlshS/M/L` 渲染成**蓝色**——
枪口火光不可能是蓝的。顺着查下去,发现是**整包素材的红蓝通道都反了**:

| 证据 | 按 v2.3 管线(BGR) | 按正确读法(RGB) | 原版事实 |
|---|---|---|---|
| 水晶矿 | 棕褐色晶体 | **蓝色晶体** | 蓝色 ✓ |
| 枪口火光 | 蓝色光球 | **橙色核心** | 橙色 ✓ |
| 爆炸 tBang | 蓝色火球 | **橙红火球** | 橙色 ✓ |
| 沙漠地图(hunters) | 蓝色地面 | **沙色地面** | 沙色 ✓ |

根因:WPE 调色板每项 4 字节,布局是 `R,G,B,0`,而
`pipeline_sprites.py / pipeline_maps.py / pipeline_ui.py` 三处都按
`(b[2], b[1], b[0])` 读,等于把红蓝对调。

**最硬的一条证据**:枪口火光 GRP 本身就是一个 3→32 的亮度渐变,
按 RGB 读是「暗蓝灰外圈 → 亮橙核心」(标准枪口火光形态),
按 BGR 读是「棕外圈 → 蓝核心」(不可能)。

v2 验收一直没发现,是因为**队伍色是管线硬编码写在 8–15 号位的**,
不受基础调色板影响——"蓝色装甲机枪兵/红色小狗"照样是对的,
于是掩盖了地面、矿、特效全反的事实。

修复:
- 三个管线脚本改为 `(b[0], b[1], b[2])` 并重跑(精灵/图标/头像/音效);
- 地图块 PNG 已烘焙了颜色,且 `badlands.vx4 / twilight.vx4` 在本重打包里
  本来就解压失败,无法重渲染——于是写了 `tools/fix_map_channels.py`
  对既有 405 张地图 PNG 做**精确等价的 R/B 通道交换**(因为
  `pal_new[v] == pal_old[v]` 恰好就是通道 0/2 对调,数学上等价)。

验证:`tools/out/fixed_sprites.png / fixed_terrain.png`——

## 八之五、v2.5:透明修复与命令卡改版

四项截图反馈全部落地,另在实现过程中揪出并修掉两个此前未被发现的交互缺陷。

### 1. 单位/建筑透明(v2.3 回归)——根因与修复

**根因**:`GameView.drawEnt()` 用 `p.setColor(Color.argb(90,0,0,0))` 画脚下阴影。
Android 的 `Paint.setColor(int)` 会**连同 alpha 一起设置**,于是紧随其后的
`c.drawBitmap(s.sheet, src, dst, p)` 被这个 alpha 调制,精灵只剩 35% 不透明;
飞行单位用的是 `argb(45,…)`,只剩 18%。水晶矿之所以看着正常,是因为它在
阴影之前绘制;选中圈/血条看着正常,是因为它们用 `Color.rgb`(alpha=255)顺带把
`Paint` 复位了——这条"顺带复位"正是 bug 能长期潜伏的原因。

**修复**:
- 两处阴影分支画完立刻 `p.setAlpha(255); p.setStyle(Paint.Style.FILL);`;
- **建筑不再画阴影椭圆**:阴影半径取 `Math.max(type.radius, tiles*14)`,对建筑
  而言比精灵本体还宽,原样就是"地上一滩黑水";
- `render()` 开头在 `c.drawColor(...)` 之后统一 `p.setAlpha(255)` 做防御性加固,
  避免将来某一层忘记还原导致整层发白。

**回归证据**(新增桌面 harness):原 `GameDesktop.drawEnt()` 根本不画阴影,
所以这类 bug 对既有工具不可见。补了 `drawShadow()` / `renderWithShadows(…, leakAlpha)`
与 `ShadowProof.java`,同一场景渲染两遍:

```
shadow_bug.png   F9B2D53A…  (leakAlpha=true) 精灵压到 35%,地形透出
shadow_fixed.png A8EFC7D6…  (leakAlpha=false) 精灵满不透明 + 底部柔和阴影
```
注意 AWT 下 `setColor(new Color(0,0,0,90))` 在 `TYPE_INT_RGB` 上只把阴影混进背景、
不产生持久 alpha,必须改用 `AlphaComposite` 才能真复现 Android Paint 的调制行为

### 瓦片集映射修正(批次六前置)

上一版"缺压缩掩码 0x20"的结论是错的:实现 0x20 **修不好任何东西**。
真实根因是 `full_decompress()` 被当成无上限的前置探测器使用——当某扇区的存储
长度已等于期望输出长度时,该扇区是**原样存储**的,其首字节是真实像素数据
(对瓦片图常为非法掩码 0x20/0x3c/0xa4),`full_decompress` 于是去 explode 原始像素。
连带修了三处耦合缺陷:新增位置性的 `is_stored_sector(sec, want)`;
`want` 改为按扇区位置推导而非跟着累计输出漂移;`stored_file` 从"只看 sector 0"
改为"每个扇区都必须是存储态"(否则 `badlands.vx4` 会静默返回 143844 而非 154734 字节)。

修完后 8 瓦片集 × 5 文件 = **40/40 全部提取成功**,含此前从未成功的
`badlands.vx4`(154734/155008)与 `twilight.vx4`(167420/167424)。

`0 badlands/1 platform/2 install/3 ashworld/4 jungle/5 desert/6 ice/7 twilight`,

## 八之六、批次六:巡逻 / 修理 + 命令卡分页

### 1. 巡逻(P)

核心早已具备攻击移动(`aiTimer = -1`),但**没有巡逻**。本轮补上,做法刻意保持极简:
巡逻不引入状态机,只把两个端点存在 `Ent` 上

```java
public boolean patrolling;
public float patrolAX, patrolAY, patrolBX, patrolBY;
```

`orderPatrol()` 记录"当前所在点"与"点击点"为 A/B,然后走 B;每当单位走完一条路径
(`update()` 里两处 `pathIndex >= path.size()` 的收尾点),`reversePatrolIfDone()`
判断自己离 B 近不近,就近则折返 A,否则折返 B。于是循环自我维持,不需要额外计时器。

### 2. 修理(R)

`repairError()` 把拒绝理由做成可读文案(目标无效 / 只能修理我方单位 / 目标未受损 /
晶体矿不足),视图据此弹红条而不是静默失败。`orderRepair()` 只接受 SCV。
修理结算按 `REPAIR_HP_PER_SEC = 6` 与 `REPAIR_COST_PER_HP = 1` 每帧扣矿,
**矿物不够时按剩余矿物比例少修**,不会白修也不会欠账;目标修满、死亡或矿尽时自动解除。

### 3. 攻击移动(A)

## 八之七、批次六收尾:打包发布 + BGM 结案

上一节(八之六)只做到代码;本轮把它变成可安装的包,并给"原版 BGM"一个结论。

### 1. 素材精简真的生效了(修了一个静默的坑)

`tools/slim_assets.py` 早已把 762 张 PNG 转成无损 WEBP、9 个 `walk.bin`
转成 `walk.bin.gz`,磁盘上素材只有 **5.7 MB**;但**上一版 v2.5 APK 仍是
22.3 MB**。原因是 `mergeDebugAssets` 是增量的:它只增不删,早就删除的
`walk.bin` / `title.png` 一直留在 `build/intermediates` 里被重新打包。
`gradle clean` 也没能清掉——必须先物理删除 `app/app/build` 整个目录再构建。

顺手确认了一件容易误判的事:APK 里的 `assets/maps/*/walk.bin` **不是**残留,
而是 aapt 的 gzip 解包行为——`walk.bin.gz` 进 APK 后会被还原成 `walk.bin`
并把 `.gz` 去掉,所以体积不变、名字变了;游戏侧 `walk.gz → walk.bin.gz →
walk.bin` 的兜底链本来就认它。`ui/title.png` 则是真的残留,已删除
(现在只剩 `title.webp`)。

**结果:APK 22.3 MB → 5.87 MB。**

### 2. release 签名包

- `app/app/build.gradle.kts` 增加 `signingConfigs.release`,指向
  `signing/xjzb-release.jks`(自签、RSA2048、有效期 10000 天),
  `versionCode 6→7`;`tools/new_keystore.ps1` 可在丢失时重建(重建后必须先卸载)。
- 本机离线缓存里没有 `lint-gradle`,release 的 `lintVital` 门禁跑不了,
  已在 `build.gradle.kts` 里关掉(`checkReleaseBuilds=false`),lint 本身是建议性的。
- 产物 `app/app/build/outputs/apk/release/app-release.apk`(5.87 MB),
  `apksigner verify --print-certs` 通过:
  `CN=XJZB AndroidPort` SHA-256 `32b8f4a4…c32a`。

### 3. 原版 BGM:结案——这份包里没有

`probe_music.py` 到 `probe_music4.py` 一直没能给那些大块命名(StarDat 没有
listfile,`sfxdata.tbl` 里也没有音乐条目)。本轮换了思路,不再猜文件名:

> MPQ 压缩块以扇区偏移表开头,而 `table[0] == (扇区数+1)*4` 是**已知明文**。
> 因此文件密钥可以直接从第一个密文 dword 解出来(seed1 的低字节只有 256 种
> 可能),再用整张表(单调、末项 == csize)验证——**完全不需要文件名**。

用这个办法解开了全部 ≥300KB 的加密块(`tools/probe_music5.py`):

| 类型 | 数量 | 说明 |
|---|---|---|
| zero fill | 15 | 全零,重打包时丢掉的空洞 |
| DOS EXE | 8 | `MZ` 开头的安装器/工具 |
| WAV | 6 | **全是音效**(unit 语音、youwin 等),无音乐 |

结论:这份盗版重打包里**不存在 BGM**。所以 `GameView` 的音乐开关按设计
no-op(`(无曲目)`),而不是坏了;以后往 `assets/music/` 丢任意 `.ogg/.wav`
即自动播放,代码无需改动。这一点已写进 `安装测试说明.md` 的已知限制。

### 4. 桌面验证台复活

`tools/slim_assets.py` 换成 WEBP/GZ 后,`GameDesktop` / `HudPreview` 双双失效:
`ImageIO` 不认 WEBP,而 `walk.bin` 已被删。本轮给两个 harness 补上:

- 类路径加 TwelveMonkeys `imageio-webp`(`tools/bin/lib/*.jar`,来自 Aliyun 镜像),
  并在静态块里 `ImageIO.scanForPlugins()`;
- 走图/可走性读取接受 `walk.bin.gz → walk.gz → walk.bin` 三种名字。

### 3. 虫族可玩:把"scv 硬编码"泛化成 race-aware 助手

v2 以来核心代码里"工人"一直字面写作 `e.type.key.equals("scv")`,人口
只认 `cc`/`depot`,卸货点写死 `refinery`/`cc`。直接加 `if (zerg)` 分支会
把同一个判断散到十几处,所以先抽助手,再让两族共用:

```java
public static boolean isWorkerType(String key) { return "scv".equals(key) || "drone".equals(key); }
public static boolean isWorker(Ent e) { return e != null && isWorkerType(e.type.key); }
public static boolean isDropOff(String key) { return "cc".equals(key) || "hatchery".equals(key)
                                                    || "lair".equals(key) || "hive".equals(key); }
public static boolean isGasBuilding(String key) { return "refinery".equals(key) || "extractor".equals(key); }
public static int supplyProvided(String key)  // cc→10 depot→8 hatchery/lair/hive→10 over→8 其余 0
```

改动点(全部是替换字面判断,不动逻辑):`orderMove`/`orderPatrol`/
`orderRepair`/`orderHarvest` 的工人判定、`updateEconomy` 的人口与自动派活、
`updateProduction` 的 `scv → W_IDLE`、`updateUnit` 的挖矿/卸货/修理/建造
四段与路径到达判定、`fire` 的即时命中集合(补 drone 近战与 ghost 步枪)。
新增 `nearestDropOff(Ent e, boolean gas)` 取代原来四处写死的
`nearestPlayerBuilding(e,"refinery"/"cc")`——气矿建筑与卸货点本来就该
分开查,原写法把两件事混在一个调用里。`buildError` 的气矿提示也从硬编码
"炼油厂必须建在气矿上"改成 `nameOf(key) + "必须建在气矿上"`,这样萃取场

**race 必须在构造器里就位。** 开局基地是在 `Game` 构造器里生成的,如果
先构造再 `game.race = "zerg"`,会得到一个"虫族旗号下的 Terran 基地"。

## 八之十六、v2.15:真机三轮反馈的根因修复(内存危机)

真机首测(玩家原话:"游玩起来没有敌人"、"其他两个种族选不了"、
"进入第一关没有地图")暴露了 v2.6 以来真机验证欠账埋下的总账——
**三个症状是同一个根因**。

### 1. 根因:SpriteBank 启动全量解码 336MB,压穿安卓堆

v2.9 时代的 SpriteBank 在构造函数里**解码 manifest 的每一行、每个队伍
变体**。144 行时代约 120MB,勉强活着;v2.10–14 三族扩容后变成
**362 张表 = 336MB 解码位图**,而安卓默认堆只有 192–256MB。
致命的是失败方式完全静默:`BitmapFactory` 在堆耗尽后**内部吞掉 OOM、
返回 null**,于是 manifest 排在堆耗尽点之后的一切——新单位表、全部
地形块、部分图标——**在设备上根本不存在**:

- 单位全部隐形 →"没有敌人"(敌方基地还在迷雾下面,更看不见);
- 地形块解码不出 → 黑屏 →"第一关没有地图";
- 选哪个族开局看起来都一样空 →"种族选不了"。

桌面验证台从发现不了这个:它的 `sheet()` 本来就是按需解码 + JVM 内存
管够,75 项断言全绿。这正是"每批必须真机"这条规矩存在的理由。

### 2. 修复(三件套)

- **SpriteBank 改懒解码**:构造函数只解析元数据 + 预解码很小的一批
  命令图标;表在首次 `get()` 时解码并缓存;**敌方变体按需**从 `_r`
  解码,不再永远搭车。开局屏解码足迹从 336MB 降到 **4MB**(84 倍);
  缺失结果也缓存(一次尝试,不逐帧重试)。
- **`android:largeHeap="true"`**:游戏类应用的正当用法,给后台大表
  留余量。
- **OOM 兜底**:`loadBitmap` 显式捕获 `OutOfMemoryError`(它不是
  Exception,原 `catch (Exception)` 拦不住),单张超大表不再能带崩
  整个游戏线程。
- 选族行触控区补到 48dp 平台最小值(v2.12 加色块时行高跟着 TextView
  走,真机上手指容易点空)。

### 3. 防再犯:GameDesktop 新增 `[memory]` 段

镜像 SpriteBank 的解码策略,把预算钉进断言:

```
[memory]
  full roster decode footprint: 336 MB across 230 keys; worst lurker_bur
  13 MB; oversized(>16MB)=0 PASS=true
  opening-screen footprint: 4 MB (budget 48) PASS=true
```

全量足迹只打印可见化(懒解码下总量不再是启动成本),**单表 16MB 上限**
和**开局屏 48MB 预算**是硬断言——以后谁再往管线里塞一张 4096 宽的表,
桌面就会红。

### 1. 拖动视野黑边(两个叠加的真因)

- **屏幕左侧一条 144px(5.5% 宽)纯黑竖带,四张截图位置分毫不动,连 UI 都

  从摄像头挖孔一侧内缩,游戏 Surface 整体右移,左边露出的是系统黑底。

  改为"地形盖满整个屏幕"——竖向半高从锚点量到屏幕上下边

## 八之三十、v2.30:WiFi 本地对战(锁步核心)

路线图最后一格「WiFi 本地对战 + 观战」的**可无头验证的那一半**落地:
`core/Lockstep.java` + `Game` 接入 + `[v230]` 段 1 项(9 个子断言),
全量 **99 项 PASS**。

### 为什么这期几乎没有新机制

v2.19/v2.20 已经把难的部分做完了:固定 30Hz 定步长、带 tick 与
实体下标的文本指令流、`stateHash` 每秒采样、RNG 固定种子——
`[v220]` 的 replay determinism 断言**已经证明**"同一指令流跑两次
结果全等"。锁步唯一要补的是**让两台机器在同一个 tick 拿到同一批
命令、并按同一顺序执行**。这一期就只写这一件事。

### 实现

- `Lockstep`:一个回合 = 一个 tick(30Hz)。每个玩家每回合必须**上报**
  (没有命令也要发心跳,否则对面永远等);全员上报后 `release()`
  按 **玩家 id 升序** 排出规范顺序并 `turn++`。规范顺序是两台机器
  唯一必须一致的东西,也是这套东西唯一容易写错的一行;
- 命令**复用回放格式**(`<verb> <idx,idx,…> <args>`),不发明新语法。
  于是**一场对战序列化出来就是一份合法回放**——网络层、回放层、
  断言层共用同一条指令通道,没有"联机专用的隐藏状态";
- `Game.lockstep` / `lockstepPlayer`:有 session 时 `recordCommand` /
  `recordOrder` 改为**先喂锁步**(而不是写本地 `replayLog`),
  `update()` 开头未 `ready()` 就**直接 return**(这一帧不推进),
  ready 则把 `release()` 出来的命令逐条 `applyCommand`——**和回放
  走的是同一个函数**;
- 本地玩家自己的命令也走同一条路,所以**本地命令在下一回合生效**。
  这不是延迟 bug,是锁步的定义;30Hz 下一帧 = 33ms,手感上等于立刻;
- **没有 session 时所有旧路径一字未改**(`lockstep == null` 时
  `recordCommand`/`update` 的分支与从前逐行相同);
- `reportHash` / `desyncTurn`:双方定期广播 `stateHash`,不一致就记下
  **最早**出问题的回合号——这是观战与回放判定"有人不同步/版本不同"
  的唯一证据,也是锁步自己修不了的那件事。

### `[v230]` 断言(9 条子断言,全部无头)

1. **到达顺序无关**:同一批命令按四种到达顺序 submit,`release()`
   出来的规范顺序**完全一致**(本轮最容易写错的一条);
2. **规范顺序 = 玩家 id 升序**;
3. **等慢机**:缺一个玩家的上报 → `ready()==false` 且 turn 不推进;
   补上立刻 ready;
4. **空回合也要心跳**:零命令的回合同样算上报;
5. **重复包不会执行两次**(同一玩家同回合第二次上报被忽略);
6. **线协议往返**:`encode`→`decode` 逐字段一致,含带逗号下标的复杂命令;
7. **坏行不抛异常**(与 `loadReplay` 同样的宽容);
8. **不同步可检出**且钉在**最早**出问题的回合;
9. **对战即回放**:一整场 session 的 `serialize()` 喂给 `loadReplay`,
   重放出的 `stateHash` 序列与联机时**逐点全等**(40 个采样点)。

## 八之三十一、v2.31:双机锁步联调(无头)——延迟/抖动/乱序下的两台机器

v2.30 证明了**一台**机器跑一条指令流 = 一份回放。但那句话对
"**两台**机器在同一批命令下保持同一状态"什么都证明不了。本期把它
**实测出来**:两个各自独立模拟的 `Game`,通过一条**有延迟、有抖动、
会乱序**的链路交换命令,逐回合 `stateHash` 全等。
`GameDesktop` 新增 `[v231]` 段 1 项(7 个子断言),全量 **100 项 PASS**。

### 新增

- `core/LockstepLink.java`:`Link`(send / poll)+ `Hub`(进程内星型中继)。
  Hub **故意不友好**:每条消息延迟 `latency + rnd(jitter)` 帧、允许
  同帧到期消息乱序投递;**不模拟丢包**——发现走 UDP 广播,指令流走
  TCP,所以"包丢了"不是这套协议的语义,延迟/抖动/乱序才是 TCP 也会
  交给应用的东西,也正是锁步必须扛住的东西。内部 `Random` 固定种子,
  同一组参数每次跑都完全一样;
- `core/LockstepPeer.java`:一台机器 = 一个 `Game` + 一个 `Lockstep` +
  一条链路。对外只有三相位:`receiveFrame()` / `sendFrame()` /
  `stepFrame(dt)`;
- `[v231]` 断言:三组链路参数(0/0/0、1/3/0、2/5/1+乱序)各跑 20 秒,
  两台机器的**每一回合** `stateHash` 全等、回合数不发散、指令日志
  逐条相同、序列化出来的回放体完全相同。

### 三个真 bug(都是"只有两台机器才暴露"的那一类)

1. **心跳在线上解不开**。`encode(0, 1, "")` 生成 `"L 0 1 "`,而
   `decode` 用 `split(" ", 3)` 要求三个字段,于是**心跳解出来是
   null 被丢掉**——一个"没什么可说"的玩家和一个"不在场"的玩家变得
   完全一样,对面于是永远等下去。修法:`encode` 对空命令不发尾空格,
   `decode` 只要两个字段、命令可省略;
2. **心跳会把真命令顶掉**。乱序链路上,同一回合的心跳可能**先于**
   真命令到达;`submitAt` 原来是"先到先得",于是把空占位存下、
   把真正的命令丢了——**只在一台机器上丢**,这就是一次静默 desync。
   修法:按内容而不是到达顺序定规则——真命令永远占位,空心跳只填
   空槽;
3. **一回合发了多次上报**。两台机器的驱动循环每帧都调一次
   `sendFrame()`,于是同一回合往线上发了 N 条上报;有延迟时它们
   先后到达,对面按先到的算,于是两台机器对"这个回合是什么"看法
   不同。修法:`LockstepPeer` 记住本回合是否已上报,
   `sendFrame()` 每回合**只发一次**,后调用是 no-op。

### 断言写错一次(记录下来)

第一版断言按**帧**比对两台机器的 `stateHash`,于是必然失败——
一台在等对面上报时是**冻结在旧回合**的,任何一帧两边的进度都
可以合法地不同。锁步保证的是"**同一回合结束后状态相同**",不是
"同一帧状态相同"。改成**按回合**取哈希再比对,断言才成立。
这一条写进断言注释了,免得下一个人再踩。

## 八之三十二、v2.32:流式分帧 + 开局握手

v2.31 的 `Link.send(String)` 假设**消息边界被保留**——进程内是真的,
**真实 TCP 上不是**。TCP 是字节流:一次 send 可能拆成两个包,两次
send 可能合成一个包。本期补上这一层并测出来。
`GameDesktop` 新增 `[v232]` 段 1 项(8 个子断言),全量 **101 项 PASS**。

### 新增

- `core/LockstepStream.java`:行分帧(`\n` 结尾 UTF-8)。选它的理由:
  指令行本来就是文本且**不含换行**(见 `commandFor`),不用转义;
  抓包/日志肉眼可读,和回放文件同一套写法;半包/粘包从"协议问题"
  降级成"接收侧缓冲区问题"——**收满一行才交付**;
- `core/Handshake.java`:开局前核对 `version/map/players/seed`
  (**致命**,任一不同就拒),`race/difficulty` 只**提示不拒**。
  拒绝消息**点名是哪一项**——"连不上"对玩家毫无信息量,
  "地图不一致:divide vs hunters" 才能让人去改;
- `LockstepLink.Hub` 新增 `chop` 模式:每行编码成字节后**按随机
  小片**交付,接收端用 `LockstepStream` 重组;并且**每次 poll 只
  放行有限片数**(`chopPerPoll`)——如果一次 poll 就把所有片喂完,
  一行永远在一次 poll 内重组完成,"半包跨帧"这个最有意思的情况
  就永远测不到。真实 socket 的 read 返回的就是"缓冲区里现在有的",
  常常不足一条完整消息。

### `[v232]` 断言(8 条子断言)

1. **切法无关**:同一串消息按 1 字节 / 3 字节 / 7 字节 / 整块 /
   混合切法喂进去,出来的行序列**全等**;含一条**中文**指令,
   所以切片会落在多字节 UTF-8 字符中间;
2. **粘包**:两条消息合成一次 `feed` → 出来两行;
3. **半包**:一行拆成多次 `feed`,补齐之前 `lines()` 为空;
4. **CRLF 容错**;
5. **握手放行**:六项全同 → `reject` 返回 null;
6. **逐项拒绝并点名**:version / map / players / seed 各改一项,
   都必须被拒**且原因里出现对应中文关键词**;
7. **race/difficulty 只提示不拒**;握手行畸形不抛异常;
8. **端到端**:把一条真实命令(`Lockstep.encode` + `LockstepStream`)
   按 **3 字节**切碎喂进去,对面解出来与直接投递**完全一致**。

### `[v231]` 顺势加强

两台机器的对拍从 3 组链路参数扩到 **5 组**,其中最后两组打开

## 八之三十四、v2.34:断线判负(超时弃权)

v2.31 的"等慢机"有一个**必须补上的反面**:对面**永远**不来怎么办?
两台机器会一起无限卡住——这在真机上就是"死机"。本期给出可判定
的规则并测出来。`GameDesktop` 新增 `[v234]` 段 1 项(7 个子断言),
全量 **103 项 PASS**。

### 规则

- 每次 `Game.update()` 发现回合未齐就 `Lockstep.stallTurns++`,
  齐了清零——**按帧计而不是墙钟**,桌面断言才能确定性推进;
- `stalledPlayer()` 说出**是谁**没上报(多个时取最小),提示能点名,
  而不是只说"网络不好";
- `STALL_LIMIT = 300` 帧 = 30Hz 下 **10 秒**。低于 10 秒会把
  "对面切后台抖一下"误判成掉线,高于 10 秒玩家会以为游戏死了;
- `forfeit(player)` **只能判一次**;判负后 `ready()` 不再等这个人
  (此后按空心跳计),于是对局能正常收尾、出结算,而不是僵住;
- **限额内回来的人不算掉线**:`stallTurns` 是**连续**等待,一次
  完整回合就清零。这条很关键——否则一次抖动多的对局会"累计"
  到掉线。

### `[v234]` 断言(7 条子断言)

1. 计数器在未齐时递增、齐了立刻清零;
2. `stalledPlayer()` 点名正确;
3. `stalledOut` **恰好在限额那一刻**为真(300 帧前一帧为假);
4. `forfeit` 只能成功一次,并记下输家/赢家;
5. 判负后 `ready()` 不再等那个人,`release()` 能推进回合;
6. **限额内回来的不算掉线**:三轮"200 帧静默 + 一个完整回合",
   `forfeitLoser` 仍为 -1;
7. **真跑一遍**:两个 `LockstepPeer`(2 延迟 + 抖动 + 乱序 + 分帧),
   一方在第 60 帧后彻底静默,跑满 16 秒——断言另一端在
   **stallTurns 恰好等于 300 的那一帧**判定弃权,且**此前每一回合
   两边状态全等**(没有为了要判负就提前发散),判负后还能继续推进。

### 断言写错三次(都记录下来)

1. `stalledPlayer()` 在刚 release 完的新回合上应当是**0**(新回合
   谁都还没上报),不是 -1;
2. 循环得跑到 16 秒——300 帧限额在第 60 帧静默之后才开始数,
   12 秒根本不够;
3. `waited`(从静默开始到判负的帧数)是 **296** 而不是 300:
   A 在 B 静默之前就已经卡在等 B 最后一条在途上报上了,所以
   "连续等待"比"静默时长"早起算几帧。**这不是提前判负**,是正确的;
   真正该断言的是 **`stallTurns` 恰好等于 300**。

## 八之三十五、v2.35:真实 TCP 环回双机对拍

到这里为止,锁步协议**全部**是在**进程内的假链路**上验证的。
那是验证规则的正确方式,也是**发现规则扛不住 socket**的错误方式。
本期用 `ServerSocket`/`Socket` 在 127.0.0.1 上跑**两个真线程
两个真连接**的对局,把同一个不变量换一个执行环境再测一遍。

### 为什么不能省

`[v231]`/`[v232]`/`[v234]` 的 Hub 是我自己写的:按帧投递、按帧
poll、按帧推进。真实 socket 没有"帧"——`read()` 返回缓冲区里现在
有的字节,可能不足一条消息,也可能是三条粘在一起;两个线程的
调度顺序不确定。这三件事组合起来足以让一个"逻辑上正确"的锁步
实现**死锁**(两边都在等对方先动)。

### 新增 `tools/TcpLockstep.java`

- 主机 `ServerSocket` 接受连接跑玩家 0,客机 `Socket` 连接跑玩家 1;
- 每端一个**读线程**:`read(buf)` → `LockstepStream.feed` → 取完整行
  (锁保护);主循环每帧只取走**已到达**的行,不阻塞;
- 关键点:**读线程与主循环分离**。若主循环自己阻塞读,两个玩家会
  互相等(都在等对方字节才肯上报),直接死锁;
- 实测(连跑 4 次):

```
tcp match commonTurns=227 diffTurns=0 aTurns=228 bTurns=227 samePerTurn=true PASS=true
tcp match commonTurns=226 diffTurns=0 aTurns=227 bTurns=226 samePerTurn=true PASS=true
tcp match commonTurns=222 diffTurns=0 aTurns=222 bTurns=223 samePerTurn=true PASS=true
tcp match commonTurns=227 diffTurns=0 aTurns=227 bTurns=227 samePerTurn=true PASS=true
```

`diffTurns=0` 每次都成立;两边回合数差 ≤1 是线程调度抖动的正常
表现(一边先跑完循环),不是发散。

### 门禁化

改完网络层必须**两样都绿**:`GameDesktop` **103 项** +
`TcpLockstep` **1 项**。前者快、覆盖广;后者慢一点但**不可替代**。

## 八之三十七、v2.37:安卓网络层(socket 壳)+ 集成 bug 修复

`net/` 四个类落地:真 TCP/UDP socket 壳。**关键性质:`net/` 不 import
任何 Android 类型**(只有 `java.net` + `core`),所以**出货的那条路径
可以在桌面无头跑通**——真 `ServerSocket`、真 `Socket`、真握手、
真对局。`GameDesktop` 新增 `[v237]` 段 1 项(5 个子断言),
全量 **105 项 PASS**(连跑四次稳定)。

### 新增 `net/`

| 类 | 职责 |
|---|---|
| `TcpLink` | 实现 `core.LockstepLink.Link`。**读线程与主循环分离**——主循环若自己阻塞读,socket 上会死锁(进程内假链路测不出这种死法);`setTcpNoDelay(true)`,40ms 的 Nagle 延迟在 33ms 一回合上就是多等一回合 |
| `LanDiscovery` | UDP 广播收发。**广播而非组播**:手机对手机常在热点/廉价路由上,不需要支持组播的 AP |
| `LanHost` | 绑定(端口 0 由系统选)→ 组信标 → accept → **先握手后给座位** |
| `LanJoin` | 连接 → 交换握手 → 返回 `TcpLink` 或一句可读的拒绝原因;全程工作线程,不冻 UI |

### 抓到的集成 bug:`recordOrder` 的命令根本没上线

`Game.recordOrder()` 是**直接**把命令交给 session 的(`Lockstep.submit`),
而 `LockstepPeer.sendFrame()` 原来只发自己 `queue()` 的待发命令——
于是**命令在本地生效、永远不发给对手**:一次"带延迟的 desync",
而且**之前所有断言都看不见**(单机测试里两端本来就是同一个进程)。
修法:`Lockstep.submitted(player)` 暴露本回合该玩家已提交的内容,
`sendFrame()` 优先发它。`[v237]` 的 `orderCrossed` 断言就是钉这条的:
主机用 `recordOrder` 下令,客机必须收到**同一条**命令。

- **慢信号(已有)**:对方还连着但不再应答(进程被杀/息屏/掉 wifi),

- `LockstepLink.Link` 加 `default boolean isClosed() { return false; }`
  —— 默认实现让**进程内 Hub 一行都不用改**(它没有 socket,不会失败),
  桌面断言因此完全不受影响;

  记录结果。`stalledOut(limit) || link.isClosed()` → `forfeit(who)`;

## 八之四十、v2.39 收尾:联机形态澄清 + 真 1v1 的缺口

这一节是**自查记录**,不是新功能。把联机链路整条走通之后回头核对
"玩家看到的到底是什么",发现一件必须写清楚的事。

### 现状:两台手机共控同一方,打 AI

`Game` 的模型是 **"一个人类(team 0)+ 一个 AI(team 1)"**
(`Game` 构造函数:玩家基地在 `starts[0]`,敌人在 `starts[1]`,
`aiUpdate` 驱动 team 1)。锁步让两台机器构建**同一张棋盘**,
于是:

- 两台机器的命令**都落在 team 0**;
- team 1 在**每一台**机器上由**各自的 AI** 驱动;
- 所以这不是 1v1,而是**合作打 AI**。

协议层没有任何问题——锁步只要求"同一回合、同一批命令、同一顺序",
它不关心命令里写的是哪一队。**缺口在游戏模型这一层**:
要 1v1,得让第二台机器**拥有 team 1** 并且**关掉 AI**。

### 真 1v1 需要什么(下一批)

1. `Game` 增加"队伍镜像"模式:把某个玩家的命令里的实体下标
   **映射到对面队伍**的对应实体。这是唯一需要小心的一步——
   下标必须两边**同序同义**,而 `[v240]` 探针已经确认两台机器
   的 `ents` 列表**顺序与队伍完全一致**,所以映射是可行的;
2. 该模式下**关掉 `aiUpdate`**(否则 AI 会和人类抢同一支军队);
3. 大厅把"房主 = team 0 / 客机 = team 1"写进 `NetSession.Config`;
4. 断言:两台机器各发一批命令(一台控 team 0、一台控 team 1),
   逐回合 `stateHash` 全等,且**两边的部队都在动**。

### 本期为什么不做

镜像队伍会改动 `applyCommand` 的语义(它现在直接按下标取实体),
而 `applyCommand` 同时是**回放**的执行入口——回放断言
(`[v220]`)与本次镜像改动是同一段代码。要在**同一次改动**里
同时保住"回放确定性"与"镜像正确",需要先把 `[v240]` 的
下标映射断言立起来。宁可留给下一批做干净,也不在半懂的状态下
动回放通道。

## 八之四十一、v2.40:联机语义"特征化断言"(把现状钉成规格)

v2.39 收尾时发现一个必须写清楚、也必须**测出来**的事:当前的
联机**不是 1v1**,而是**两台手机共控同一方、打 AI**。
本期把这个语义**钉成断言**,让它从"意外行为"变成"被写明的行为"——
以后要改就得**同时改这段文字**,不能悄悄变。
`GameDesktop` 新增 `[v240]` 段 1 项(4 个子断言),全量 **108 项 PASS**。

### 为什么必须钉住

`Game` 的模型是"一个人类(team 0)+ 一个 AI(team 1)"。锁步让两台
机器构建**同一张棋盘**,所以两边的命令**都落在 team 0**,而 team 1
由**各自的 AI** 驱动。这不是协议的问题——锁步只要求"同一回合、
同一批命令、同一顺序",它不关心命令里是哪一队——而是**游戏模型**
这一层的现状。

### 真 1v1 为什么不是小改动(已查明并记录)

命令格式用**共享 `ents` 列表的下标**标识单位
(`move 0,2,5 300 400`)。这个列表随造兵/阵亡**增删**,而两支队伍
占的那两半**各自独立变化**——所以"我这边下标 i"和"你那边下标 i"
在某队造出一个兵之后就**不再指同一个单位**。因此**按下标镜像
是不可靠的**,真 1v1 需要改成"队伍相对下标"或"每队一个实体列表",
那是**命令格式的改动**;而 `applyCommand` **同时是回放的执行入口**,
所以它必须与回放确定性断言(`[v220]`)在**同一次改动**里完成。
`[v240]` 的注释把这些都写在断言旁边了。

### `[v240]` 断言(4 条子断言,全部真 socket)

1. 两台机器的 `ents` 列表**顺序与队伍完全一致**——这正是"下标式
   命令流"能在两端通用**的前提**;
2. **任一方**发的命令都能到达两端,并作用在 team 0 上;
3. team 1 仍然由 AI 驱动(所以只有一方人类的对局**仍有对手**);
4. 做这件事的同时两台机器**保持锁步**(逐回合 `stateHash` 全等,
   实测约 90 回合、`diffTurns=0`)。
