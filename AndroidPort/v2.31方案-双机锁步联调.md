# v2.31 方案:双机锁步联调(无头)——延迟/抖动/乱序下的两台机器

> 前置状态:v2.30 已出包(99 项断言 PASS,`Lockstep` 核心 + `Game` 接入)。
> v2.30 证明了**一台机器**跑一条指令流 = 一份回放;
> 但"**两台**机器在同一批命令下保持同一状态"这件事,还只停留在
> 单机的推理上。本期把它**实测出来**。

---

## 本期要证明的一句话

> 两台各自独立模拟的 `Game`,通过一条**有延迟、有抖动、会乱序**的
> 链路交换命令,每回合的 `stateHash` 逐点相同。

这是整个联机功能唯一真正重要的性质。它不需要两台设备,不需要
socket——只要一个**确定性的、可注入坏毛病的**链路模型,就能在
`GameDesktop` 里跑出来。

---

## 批次A:`core/LockstepLink.java` + `core/LockstepHub.java`

- `LockstepLink`:两个方法的最小接口
  ```java
  void send(String line);      // 发出去,不等待
  List<String> poll();         // 取回本帧到达的行
  ```
  安卓侧将来的 TCP 实现只是把它包一层 socket;桌面断言用它做
  进程内实现。**协议逻辑不依赖任何 Android 类**,所以能无头测。

- `LockstepHub`:进程内的 N 端星型中继,故意做得**不友好**:
  - `latency` / `jitter`:每条消息延迟 `latency + rnd(jitter)` 帧;
  - `reorder`:允许同一帧到期的消息**乱序**投递;
  - **不丢包**——这是有意的:方案里发现走 UDP 广播、指令流走
    TCP(或可靠 UDP),所以"丢包"不是这套协议的语义。乱序与延迟
    才是 TCP 也会给的东西,也正是锁步必须扛住的东西;
  - 内部 `Random` 固定种子 → 同一组参数跑两次**完全一样**,
    断言可以复现。

---

## 批次B:`[v231]` 断言(两台机器,全程对拍)

1. 用同一张图的**同一份** walk/starts/units 构造两个 `Game`
   (各自独立 `new`,不共享任何可变状态);
2. 各挂一个 `Lockstep(2)` 与一条 `LockstepHub` 链路;
3. 每帧:两端各自上报(玩家 0 每隔一段时间下命令,玩家 1 只发心跳),
   `hub.pump()` 投递,两端 `update()`;
4. 每 30 帧比对 `stateHash`——**全等**才算过;
5. 三组链路参数各跑一遍:`latency=0`、`latency=1+jitter=3`、
   `latency=2+jitter=5+reorder`。**参数越坏,结论越硬**;
6. 另外断言:两端的**已释放回合数**一致(不会一边跑在前面);
7. 以及:两端各自序列化出来的回放**内容相同**(规范顺序的唯一性)。

### 断言的边界

- 不测 socket、不测安卓 UI(下一批);
- 不测"丢包恢复"(协议语义里没有丢包);
- 不测 3 人以上(锁步的规范顺序是 N 人的,但两台机器是本期的目标)。
